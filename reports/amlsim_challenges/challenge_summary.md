# AMLSim Synthetic UPI & 3 Controlled Challenge Cases Report

## 1. Experimental Overview
- **Base Dataset**: Synthetic UPI transaction graph generated via IBM AMLSim (20,000 nodes, 120,558 transactions, 200 cycles, 200 fan-in patterns).
- **Train Period**: Steps 1 to 75 (past-only online features, multi-epoch causal GraphSAGE training).
- **Validation Period**: Steps 76 to 90 (blend weight grid search & threshold calibration).
- **Evaluation Period**: Steps 91 to 149 (unseen out-of-time test stream).
- **Rank-budget metric**: top 1.0% of evaluated transactions (Section 2).
- **Validation-Calibrated Blend**: `0.25 * xgb_score + 0.75 * gnn_score` with production alert cutoff at `0.3020`.
- **Causality**: XGBoost features are past-only; GraphSAGE is trained and validated on causal snapshots (each step sees only earlier steps, running-mean node features) and test/serving use the identical evolving-graph code path.

## 5. Analysis of the Three Challenge Scenarios (numbers generated from this run)

### Challenge 1: Disguised Suspicious Behavior
- **Test**: Launderers split transfers into micro-ticket sizes (INR 115-485) and introduce randomized delays (+3 to +13 steps) strictly within split boundaries.
- **Result**: Blend AP 0.8412 (baseline) -> 0.7709; recall at the deployed threshold 58.6% -> 51.2%. XGBoost AP 0.7777 -> 0.6944, GraphSAGE AP 0.8400 -> 0.7447.

### Challenge 2: Benign Lookalike Hubs
- **Test**: Legitimate high fan-in merchant QR hubs and high fan-out corporate payroll accounts were injected with collision-free transaction IDs.
- **Result**: 235 of 835 benign hub events (28.1%) are alerted at the deployed threshold. Pure-behaviour features cannot fully separate a busy legitimate merchant from a collection mule; a verified-merchant registry is needed for that (see the consumer copilot).

### Challenge 3: Partial / Missing History
- **Test**: 50% of earlier edges were withheld before scoring to simulate cold-start / unobserved cross-bank history.
- **Result**: Blend AP 0.8412 (baseline) -> 0.8323; alert rate 5.13% -> 4.96%, recall 58.6% -> 58.3%. The `insufficient_history` flag is raised so the API can warn operators instead of giving unwarranted confidence.

## 6. Threshold transfer (validation -> test)
- Policy: `fixed_alert_budget_on_validation` with a 5.0% validation alert budget -> cutoff 0.3020.
- Validation: precision 80.8%, recall 62.4%, alert rate 5.0%.
- Test (baseline), static cutoff only: precision 81.7%, recall 75.3%, alert rate 7.67% (scores drift upward over time because cumulative-count features grow, so a fixed cutoff over-alerts).
- Test (baseline), deployed policy with rolling budget: precision 95.3%, recall 58.6%, alert rate 5.13%.
- Reference only: the previous max-F1 cutoff would have been 0.4597.

## 7. Known limitations
- All data here is simulated (AMLSim). The 'UPI' handles are labels attached to simulated accounts, not real UPI traffic.
- Challenge scenarios are generated by this project's own scripts, so they test the model against the authors' own assumptions.
- Laundering prevalence (~8%) is far above real-world AML base rates, so precision numbers are optimistic.
