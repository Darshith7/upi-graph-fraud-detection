# Data guide

This project is about **UPI** payment fraud and mule accounts. **No public UPI transaction dataset
exists** (NPCI does not publish transaction-level data), so everything the served model is trained or
tested on is **simulated**. Nothing here has been validated on real UPI traffic.

## What is used

| Dataset | Role | In the repo? | How it is produced |
|---|---|---|---|
| AMLSim 20K network (`data/amlsim_raw/20K_fanin200cycle200`) | Training / validation / test of the served model | Yes | Pre-generated IBM AMLSim output (Apache-2.0, see `external/AMLSim/LICENSE`) |
| Challenge scenarios (`data/amlsim_challenges/*.csv`) | Baseline + 3 stress tests (disguised amounts, benign hubs, missing history) | Yes | `python src/prepare_amlsim_challenges.py` (seeded) |
| Held-out UPI simulation (`data/upi_holdout/upi_sim_holdout.csv`) | **Zero-shot** test; never used for training | Git-ignored, regenerate | `python src/generate_upi_simulation.py` (seed 7, deterministic) |
| Verified-merchant registry (`data/verified_merchants.json`) | Merchant exemption in the consumer copilot | Yes | `python src/build_verified_merchant_registry.py` (seeded from the simulation; replace with a KYC-backed list in production) |

AMLSim handles such as `acc_00123@okhdfcbank` are labels attached to simulated accounts. Models use
only node ids, timestamps and amounts; handle strings are never model inputs.

## The held-out simulator (`src/generate_upi_simulation.py`)

Independent of AMLSim and written to different assumptions: UPI-style P2P and merchant-QR payments,
Zipf merchant popularity (busy merchants = benign hubs), payroll runs, a hard INR 1,00,000 per-payment
limit, diurnal activity, ~1 payment per person per day, ~0.7% laundering, and five mule typologies
that the training data does not contain (collection mule of 8-80 senders, relay chain, structuring,
circular ring, fresh-account scam burst).

Honest caveats:

* It is the authors' own model of UPI: independent of AMLSim, **not** independent of the authors.
* Version 1 had a shortcut (laundering amounts far above normal; one feature gave ROC-AUC 0.98).
  It was fixed once, before the final evaluation, and not tuned against the model's score. Amount is
  still the single most informative feature (ROC-AUC about 0.85), so a model trained *on* this simulator
  scores very high (AP 0.995). Use it to test **transfer**, not absolute performance.
* `tests/test_system_components.py::test_holdout_simulator_is_valid_and_not_trivial` guards the limits,
  determinism and the amount shortcut.

## Optional non-UPI datasets (from the original proposal)

The IBM AML, Bank Account Fraud (BAF) and IEEE-CIS parts of the repo are **generic financial-fraud**
benchmarks, not UPI. They are optional and **not needed** for the API, tests or any UPI result.

| Dataset | Where | Needs |
|---|---|---|
| IBM AML `HI-Small_Trans.csv` | Kaggle `ealtman2019/ibm-transactions-for-anti-money-laundering-aml` | Kaggle account |
| Bank Account Fraud (Feedzai, NeurIPS 2022) | Kaggle `sgpjesus/bank-account-fraud-dataset-neurips-2022` | Kaggle account |
| IEEE-CIS Fraud Detection | Kaggle competition `ieee-fraud-detection` | Kaggle account + accepting the competition rules |

With your own Kaggle API token (`~/.kaggle/kaggle.json`) you can fetch them, for example:

```bash
pip install kaggle
kaggle datasets download -d ealtman2019/ibm-transactions-for-anti-money-laundering-aml -p data/raw --unzip
```

The BAF and IEEE-CIS evaluation scripts in this repo currently run on **synthetic stand-ins generated by
the scripts themselves** (see the README); they have not been run on the real files.
